# Booster-Chip Data Plane Security Red-Team Report

**Scope:** P2 / `jeff` / line-one Booster-Chip data plane.  Static review of
chip identity, sparseimage vault handling, card-tamper consequences,
`mcp_proxy.py` routing and removal handling, and pairing.

**Mode:** Report-only.  No production code was changed.  Findings assume an
attacker can write the unencrypted card surface; findings involving host state
explicitly say so.  Severity reflects impact on the trust claims in the current
protocol, not merely exploit complexity.

## Findings

| id | file:line | finding | severity | recommended fix |
|---|---|---|---|---|
| RT-01 | `jeff:127-155`; `chip/init.sh:226-257` | **A tampered heartbeat can spoof any chip identity past the SHA-256 check.** `identity_hash` is an unkeyed, self-authored digest stored beside the data it covers, so a card writer can change `device_id`, label, model, tool-chain root, vault mount name, or other fields and recompute the digest exactly as init does.  More directly, verification skips the digest comparison when `identity_hash` is empty.  The hash detects accidental corruption only; it provides no authenticity. | **critical** | Authenticate a canonical manifest with a host-trusted Ed25519 signature (or MAC with an off-card key), require a present, correctly typed signature/hash, pin the device public key or certificate during pairing, and reject identity changes after enrollment. |
| RT-02 | `jeff:130-145`; `chip/CHIP_SPEC_v1.0.md:65-74` | **The implementation hashes the intended logical JSON representation, but not the original file bytes, and comparison is not timing-safe.** It parses JSON, blanks `identity_hash`, and hashes `json.dumps(..., sort_keys=True, ensure_ascii=False)`; init and update paths use the same serialization, so ordinary formatting changes do not matter.  This is broadly consistent with the specification's parse-and-canonicalize procedure, although it does not explicitly select UTF-8 when reading and its “canonical” encoding retains default separator spaces.  Comparison uses `computed != stored`, not `hmac.compare_digest`.  Timing is not the primary weakness because the digest is public and freely recomputable, but it still fails the requested constant-time property. | **medium** | Define one byte-exact canonicalization (for example RFC 8785/JCS), open as explicit UTF-8, validate a 64-character lowercase hex digest/signature, and use `hmac.compare_digest`; more importantly, replace the self-hash with an authenticated signature as in RT-01. |
| RT-03 | `jeff:133-144`; `chip/CHIP_SPEC_v1.0.md:242-250` | **Protocol validation is fail-open for missing, zero, negative, string-like, and legacy versions.** The verifier rejects only values greater than 1 and defaults a missing protocol to 0, while the frozen protocol requires exactly integer `1`.  Some malformed types cause a traceback/denial of service rather than a clean rejection. | **high** | Require an exact schema before using any field: `type(protocol) is int and protocol == 1`, required fields present with bounded types/lengths, UUID/timestamp validation, and fail closed with a controlled error. |
| RT-04 | `jeff:220-240`; `jeff:615-644`; `chip/init.sh:104-110` | **Card write access becomes host code execution.** Activation starts `${volume}/mcp/server.py` directly from the unauthenticated, unencrypted card surface immediately after checking only heartbeat JSON.  The specified encrypted-vault firmware structure and checksum are neither mounted nor verified at activation.  A malicious card can therefore provide a valid-looking/rehashed heartbeat and arbitrary Python executed with the user's privileges. | **critical** | Never execute code from the writable surface.  Run a minimal host-owned server and treat card content as data; if extensibility is required, verify a signed manifest plus every executable byte against a pinned issuer, copy to a quarantined immutable location, sandbox with least privilege/no network, and perform all validation before launch. |
| RT-05 | `chip/init.sh:272-303`; `jeff:757-770` | **The vault passphrase is not intentionally written to the card or placed in command-line arguments/log output, but handling is unnecessarily exposed in process memory and pipes.** It is read silently into a shell variable and sent to `hdiutil -stdinpass`; the sparseimage necessarily stores only encryption metadata, not the plaintext passphrase.  The variable is not exported and normal stdout does not print it.  However, it persists in the long-lived shell variable, is duplicated by `echo`/pipes (and on retry), is not explicitly cleared, and may be exposed to same-user tracing/debugging, crash capture, or shell instrumentation. | **medium** | Prefer a dedicated credential file descriptor or OS credential API with echo disabled, avoid shell string copies, clear/unset passphrase variables immediately after use (including failures/traps), disable tracing around secret handling, document memory/process-threat limits, and add tests asserting logs/card files never contain test passphrases. |
| RT-06 | `jeff:715-821`; `jeff:963-1003`; `chip/CHIP_SPEC_v1.0.md:215-227` | **“Read-only” is a label, not storage enforcement.** `hdiutil attach` is invoked without `-readonly`; `flip` only rewrites `.jeff-state.json` and an environment variable in the CLI process, without remounting the filesystem or restarting the already-running MCP.  Thus a process with filesystem access—and potentially card-delivered code from RT-04—can modify decrypted credentials/state even while Jeff reports read-only. | **high** | Attach with `hdiutil ... -readonly` for read-only mode; implement flips as detach/reattach with the correct OS-level mount flags, restart confined consumers, verify actual mount flags before reporting state, and deny writes in both filesystem permissions and the MCP authorization layer. |
| RT-07 | `jeff:598-660`; `jeff:780-793`; `jeff:855-924` | **A writable card can rewrite all mutable security/accounting claims, and host code helps legitimize them.** There is no pinned prior identity, signature, monotonic counter, or trusted audit record.  An attacker can reset/inflate `mount_count`, alter the tool-chain identity/model/vault name, forge the public vault manifest, replace the sparseimage (causing denial of service or passphrase capture attempts via malicious code), and alter datasets/models/indexes.  Activation then records attacker-controlled values into host state. | **high** | Pair and pin immutable identity off-card; maintain monotonic counters/audit evidence in trusted host storage; sign manifests and content hashes; verify the sparseimage/firmware provenance before access; treat public manifests, models, indexes, and datasets as untrusted inputs. |
| RT-08 | `mcp_proxy.py:288-305`; `mcp_proxy.py:373-422` | **Card reads have traversal and symlink escapes.** `normpath` plus string `startswith(volume)` accepts sibling-prefix paths (for example volume `/mnt/chip` and request `../chip-secret/file`) and does not stop an on-card symlink from resolving outside the card.  Since `volume_path` comes from writable host state, a state-file writer can route reads to any directory. | **high** | Resolve both root and target with `realpath`/`Path.resolve`, require `os.path.commonpath([root, target]) == root`, reject symlinks or walk with `openat`/`O_NOFOLLOW`, constrain activated roots to an allowlisted mount namespace, and protect/validate the state file.  Apply the same fix to `chip/mcp_server.py:92-115`, which has the same prefix check and also references undefined `path`/`safe_name` variables. |
| RT-09 | `mcp_proxy.py:893-938`; `mcp_proxy.py:941-969`; `mcp_proxy.py:972-1037` | **Dynamic routing trusts host registry/state paths and an attacker-controlled heartbeat mount name without containment or mount-identity checks.** Relative registry paths may contain `..`; absolute paths are accepted; `.chip-mount.json` can nominate an arbitrary existing directory; and heartbeat `vault_volume_name` is joined under `/Volumes` without validation (an absolute value overrides the prefix, and `..` can escape it).  The proxy then discovers `vault-*` directories and databases at that location, enabling unintended file/database access and writes through MCP if either state/registry is writable or heartbeat fallback is attacker-controlled. | **critical** | Make state/registry owner-only and atomically written, schema-validate names and paths, reject absolute/`..` components from card fields, canonicalize and contain all resolved paths, bind mountpoints to the expected image/device using OS mount metadata, and never let card metadata select a host filesystem root. |
| RT-10 | `mcp_proxy.py:35-63`; `mcp_proxy.py:288-297`; `mcp_proxy.py:983-1023` | **`VolumeGoneError` coverage is partial and removal handling is fail-soft/inconsistent.** File/list operations translate broad I/O failures, and vault discovery auto-deactivates a missing registry entry, which is a useful clean degradation.  But `_active_state` reads/parses state without safe wrappers; JSON decode and races can escape.  Numerous `isfile`/`isdir`/`getsize` checks occur outside guarded operations; several scan branches silently keep partial results; and auto-deactivation updates only the active-volume list—it does not revoke state, kill the card MCP, close database handles, or unmount the vault.  A remove/replace race can also redirect later path operations. | **high** | Centralize per-request routing in a validated snapshot containing device/mount identity; catch decode and removal errors at the tool boundary; use descriptor-relative operations to reduce TOCTOU; on disappearance revoke all leases, stop the MCP, close DBs, detach the vault, clear state, and return a uniform typed error. |
| RT-11 | `chip/CHIP_SPEC_v1.0.md:133-145`; `chip/init.sh:312-344`; `reconcile-cards.py:75-76` | **Pairing is not implemented.** Init creates an empty `trust/` directory but generates no device key, certificate, or signed chain; activation performs no enrollment, host trust lookup, challenge-response, or user confirmation.  Runtime reconciliation explicitly describes elevated pairing as future work.  Consequently any clone/rehashed heartbeat is accepted and there is no way to distinguish a previously paired chip or revoke it. | **critical** | Implement explicit first-use pairing with a human-verifiable code, device-generated non-exportable Ed25519 key, host-side pinned public key/certificate and policy, fresh nonce challenge-response on every activation, signed content manifest, revocation/rotation, clone detection, and immediate lease revocation on removal. |

## Clean / Lower-Risk Areas Observed

- **Hash coverage is internally consistent:** init, verification, mount-count update,
  and vault-manifest update all blank `identity_hash` and hash a sorted JSON
  serialization (`chip/init.sh:253-257`, `jeff:139-145`, `jeff:780-793`, and
  `jeff:913-921`).  This makes formatting-only edits harmless.  It does **not**
  provide authenticity (RT-01).
- **No plaintext key persistence was found:** reviewed vault creation and mount
  flows pass the secret on standard input and do not deliberately write it into
  `heartbeat.json`, `.jeff-state.json`, the card surface, or the MCP log
  (`chip/init.sh:272-303`; `jeff:757-770`).
- **Default vault contents are placed under encryption:** credentials, state,
  logs, and keeper material are created only after the encrypted sparseimage is
  attached (`chip/init.sh:300-344`).
- **SQL values in dynamic vault operations are parameterized:** the reviewed
  query and execute helpers accept parameter tuples, and representative vault
  operations use `?` placeholders (`mcp_proxy.py:66-100` and
  `mcp_proxy.py:1213-1229`).
- **Removal errors are presented without a raw crash in the primary card-read
  tool:** `chip_read_card` catches `VolumeGoneError` and returns an actionable
  ejection hint (`mcp_proxy.py:388-422`).

## Priority Order

1. Stop executing untrusted card code (RT-04) and prevent arbitrary proxy roots
   (RT-09).
2. Add real pairing and signed identity/content verification (RT-01, RT-11),
   then pin identity off-card.
3. Enforce storage-level read-only mounts and reliable removal revocation
   (RT-06, RT-10).
4. Harden path containment, schemas, canonicalization, and secret lifecycle
   (RT-02, RT-03, RT-05, RT-08).
